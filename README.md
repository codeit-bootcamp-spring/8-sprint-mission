## Java 기반 채팅 서비스 (Sprint Mission)

- Java 와 객체지향 설계를 기반으로 User / Channel / Message 도메인을 구현하고,<br />
  JCF 기반 저장 방식과 File I/O 기반 영속화 방식(직렬화), 그리고 관심사 분리를 적용한 프로젝트입니다.


- 해당 프로젝트는 Codeit 백엔드 스프링 트랙의 Sprint Mission 2 과제로 진행되었습니다.


## 주요 기능

**User / Channel / Message CRUD**

- 사용자 생성 / 조회 / 수정 / 삭제

- 채널 생성 / 조회 / 수정 / 삭제

- 메시지 생성 / 조회 / 수정 / 삭제

**저장소 선택 가능 (Repository 교체)**
- JCF 기반(In-Memory Map)
- File IO 기반(.ser 파일 직렬화 저장)
- AppConfig에서 구현체만 바꾸면 전체 동작 변경 가능

**Basic, AppConfig**
- 심화 요구사항에서는 `Basic*Service` 레이어 구현이 제시되었습니다.
- 본 프로젝트에서는 Basic 레이어를 구현은 완료하였으나 AppConfig 기반의 DI 구조를 선택하였습니다.

**AppConfig의 기능**

- Repository(JCF/File) 구현체 선택
- Service 구현체 생성 및 의존성 주입
- 비즈니스 로직과 저장 로직의 완전한 분리

**AppConfig의 선택 이유**

- 저는 해당 클래스를 구현하는게 구조가 더 단순하고, 명확해 보였습니다.
- 저장 방식 교체가 AppConfig 한 곳에서 해결되고,
- 실제 스프링에서 사용하는 @Configuration + @Bean 구조와 동일하다 생각하였습니다.
- 서비스는 저장소 구현체를 전혀 몰라도 되며 저장 방식(JCF/File)은 오직 AppConfig에서 결정 됩니다.

### JCFService vs FileService 비교 (공통점 & 차이점)

**공통점**

- 동일한 서비스 인터페이스 구조를 지닌다.
- 클라이언트 코드는 구현체에 의존하지 않는다.
- 비즈니스 로직의 흐름이 동일하다.

**차이점**

- 두 구현체는 어디에 저장할지와, 어떻게 불러오는가의 차이가 존재한다.


| 구현체        | 저장 방식                                   | 특징                    |
|---------------|---------------------------------------------|-------------------------|
| JCF Service   | Map<UUID, Entity> 메모리 저장               | 휘발성(종료 시 사라짐) |
| File Service  | 직렬화(.ser) 파일 저장                       | 영속성 제공             |


| 구현체       | 읽기 방식                    | 작동 원리   |
|--------------|--------------------------|---------|
| **JCF**   | Map에서 직접 get() | 메모리 접근 → 매우 빠름 |
| **File** | ObjectInputStream으로 역직렬화하여 List로 복원          | 파일에서 가져오므로 속도는 느리지만 값 유지  |


| 구현체      | 데이터 유지                   |
| -------- | ------------------------ |
| **JCF**  |프로그램 종료 시 모두 사라짐          |
| **File** | 파일에 저장되므로 재실행해도 동일 데이터 유지 |

| 구현체      | 속도                    |
| -------- | --------------------- |
| **JCF**  | 메모리 기반 → 매우 빠름        |
| **File** | 파일 입출력(IO) → 상대적으로 느림 |
